# 选题方案：AI 交叉质询评审团

> **题目名称**：AI 交叉质询评审团 —— 面向高校学生方案的答辩陪练与能力诊断系统
> **一句话定位**：学生提交自己的方案（毕设开题 / 大创 / 竞赛），4 位不同视角的 AI 评审轮流质询、**并且互相接话**，逼学生把方案想透，最后输出「你没答好的问题清单」。

---

## 一、为什么做这个（背景与痛点）

**用户**：要开题答辩的本科生、大创/挑战杯/互联网+ 参赛队、准备预答辩的研究生。

**痛点**：

1. **被问懵是常态**：开题/答辩现场，评委三句话就问到方案的软肋，学生当场答不上来，平时却没有任何地方可以练。
2. **找不到人陪练**：找同学模拟提问，同学问不出专业问题，也问不到第二层。
3. **大模型一对一问答太"温柔"**：你问它答，它不会主动挑你毛病，你根本不知道自己哪里没想到。

**现有 AI 方案不够用的地方**（这是本选题的立足点）：

| 现有做法 | 不行在哪 |
|---|---|
| ChatGPT 式问答 | AI 被动应答，学生不知道该问什么 |
| 单一 persona 的"AI 评委" | 一个视角问到底，问不深，没有交叉火力 |

---

## 二、核心突破点（一句话能讲清、评委一听就懂）

> **让 AI 评审之间也互相质询。**

真实答辩现场最有杀伤力的，不是某个评委问了一个难题，而是**评委 B 接过评委 A 的话**：
"你推荐的这套技术方案，他刚才说的预算根本撑不住。"

本系统把这个行为做出来：评审发言后会广播给其他评审，其他评审判断"这句话是否触碰到我的关注点"，命中就**主动接话、当场反驳**。这是 **agent 与 agent 之间的对抗**，不是"四个 AI 各问各的"。

这是本选题区别于 A05（单人考官）、A12（授课/RAG）的根本差异，也是技术上真正需要设计的地方。

---

## 三、四位评审的人设

每位评审 = 一个「关注点清单 + 提问风格 + 追问触发条件」的 persona。

| 评审 | 关注点 | 典型提问 |
|---|---|---|
| **技术评审** | 可行性、是否过度设计、有没有更简单的方案、关键难点 | "为什么必须用大模型？规则引擎做不到吗？" |
| **成本与进度评审** | 预算、人力、周期、里程碑是否现实 | "按 5000 用户算，每月 API 成本多少？" |
| **合规与伦理评审** | 数据来源合法性、隐私、算法偏见 | "这些数据你是爬的还是买的？有授权吗？" |
| **用户与价值评审** | 谁真的会用、相比现有方案优势、是不是伪需求 | "已经有现成平台了，同学为什么要换？" |

## 四、系统流程

```
1. 提交方案        粘贴文本 / 上传 Word、PDF、PPT
        ↓
2. 方案要素抽取    目标 | 技术方案 | 预算 | 进度 | 风险 | 合规 | 用户
        ↓
3. 立项评审会      ┌─ 第 1 轮：4 位评审依次提主问题
                   ├─ 交叉质询：任一评审可接话反驳（每议题上限 1 次，防跑偏）
                   ├─ 学生回答：本议题的问题**按提问顺序一条一条答**，答不上来可以跳过
                   └─ 追问：都答完后，还没被说服的那位再追一层（每议题上限 1 层）
        ↓
4. 会议纪要        质询记录时间线 + 未答好的问题清单（按严重度排序）
        ↓
5. 能力诊断        四维评分（可行性 / 完备性 / 严谨性 / 表达）+ 雷达图   ← 本轮不做
```

> **前端形态**：两个智能体（模拟面试 / 交叉质询评审团）放在**同一个页面**里，左侧栏顶部用按钮切换，
> 默认进模拟面试。评审会本身不是"聊天"，但它的交互骨架（提交 → 被追问 → 回答 → 出结论）
> 和对话是一致的，所以共用一套 ChatGPT 式外壳：左边窄侧栏（切智能体 + 历史记录）、
> 中间居中的消息流、底部圆角输入框。历史记录存浏览器本地，后端仍按 `session_id` 记着上下文，
> 所以刷新和重开都能接回上一场；开完的评审会还能从库里读回来只读回看。

## 五、三个关键机制设计（这是真正要动脑的地方）

### 机制 1：交叉质询（核心创新）

- 每个评审发言后，把发言内容 + 关注点广播给其他评审
- 其他评审输出结构化判断：`{want_to_speak: bool, reason, question}`
- **防跑偏**：① 每个评审每轮最多接话 1 次；② 接话必须与自身关注点相关（prompt 强约束）；③ 全会话交叉质询总次数上限
- 没有这个约束，4 个 AI 会无限互怼，会议永远开不完

### 机制 2：发言调度

不能让 4 个评审同时刷屏。用图结构 + state 控制：

```
manager(调度中枢)
  ├─ 依据 round / speaker_index / meeting_phase 决定下一个发言者
  ├─ 第 1 轮：技术 → 成本 → 合规 → 用户（顺序）
  ├─ 每个议题之间：插入 0~1 次交叉质询
  └─ 学生答完：回到提问的那位评审做「是否追问」判定
```

一个议题的完整状态机（`meeting_phase`）：

```
main(提主问题) → cross(别人接话) → await_answer(停住，等学生答第 1 问)
                                        ↓ 学生答完，另发一次请求
                                     judge(由这一问的提问者判定)
                                        ↓
                              advance: 看整个议题决定下一步
                                 ├ 还有没答的问题 → await_answer(第 2 问)
                                 ├ 都答完了，有人没被说服 → followup(他追一层)
                                 └ 都答清楚了 → 换下一位评审
```

**一个议题里可能好几位评审都问了话**（主问题 + 接话），学生**按提问顺序一条一条答**，
每条由**那条问题的提问者**判定 —— 谁的疑问谁负责。

关键点：**`await_answer` 是 `goto=END`**，也就是说会议不是一次请求跑完的，
而是"问一句、停一下、等学生答"。停下来时的状态由**检查点**保存，
学生答完带着同一个 `session_id` 再发一次请求，图从检查点接着跑。

> 这条规则是照着**实际界面截图**改的：第一版让"主问题 + 接话"两个问题同时抛出去，
> 却只让学生答主问题，结果是"三个评审都在问我，我该答谁"，
> 而且**接话问出口了却永远没人答、也不判定**，等于白问。现在每条问题都有问有答有判定。

> 完整的状态机、每个节点读什么状态写什么状态、分支条件、以及"想改东西改哪里"，
> 见 **`docs/评审团流程图与状态说明.md`**（Mermaid 画的，纯文本可直接编辑）。

### 机制 3：逐问题判定，而不是打总分

- 学生每答一个问题，评审输出：`{resolved: 答好了 / partial: 答偏了 / unresolved: 没答 }` + `severity(1~5)`
- 最终产出的**不是**"你的方案 78 分"，而是：
  > **你有 6 个问题没答好，其中这 2 个是致命的：**
  > ① 数据来源合法性（合规评审，严重度 5，问了两遍都没答）
  > ② 每月 API 成本（成本评审，严重度 4，答了但没给数字）
- 这才是学生真正需要的东西，也是答辩时的演示爆点

## 六之一、记忆策略：一套基础设施，两种用法

项目里有两个模块，对"记忆"的需求正好相反，所以走的是两套策略，而不是无脑上全套。

| | 模拟面试（原有模块） | 交叉质询评审团（本方案） |
|---|---|---|
| 交互形态 | 多轮问答，可以聊很久 | 一场会议，问一句停一下 |
| 要跨会话记住吗 | 要：同一个学生下次再来，得记得他的画像和历史 | 不要：一场评审一次性结束 |
| 用到的记忆 | 窗口 / 摘要 / 长期 / 画像，四层齐全 | 只有一个**检查点** |
| 载体 | Redis + PostgreSQL + Chroma | PostgreSQL 检查点（与面试共用同一个 saver） |
| 说话人的上下文从哪来 | 四层记忆拼成提示词注入 | 图的 state（`question_log` 本身就是短期记忆） |

**为什么这么定：**

1. **评审不需要"外挂记忆"，因为状态机本身就是短期记忆。** 全场问答都记在 `question_log` 里，
   本议题的上下文由它拼出来喂给评审。再往 Redis 存一份窗口记忆，是同一份数据存两遍。
2. **摘要记忆是给"上下文会被撑爆"的场景准备的。** 评审会有轮次上限（默认 1 轮 + 每议题追问 1 层），
   撑不爆，用不上。
3. **长期记忆和画像记忆是按用户跨会话攒的。** 一场评审开完就结束了，没有"下次"可攒。
   真要做"同一学生多次提交"的纵向追踪，该用 `student_id`（`review_session` 表里有），
   而不是前端那个随浏览器生成的 `user_id`。
4. **检查点不是"够用"，是刚需。** 学生回答是另一次 HTTP 请求，
   会议必须能从检查点续上，所以评审模块也接了 PostgreSQL 检查点。
   两个模块共用一个 saver，靠 `thread_id` 区分（面试是 `session:<uuid>`，评审是会议 id），不会串。

**直接收益：** 不需要向量库、不需要知识点树、不需要为记忆做增量摘要，
工程量和不可控点都比同类方案少一截。

> 要强调的是：**记忆是通用基础设施，不是本方案的卖点。**
> 本方案的差异在第二节说的"agent 与 agent 对抗"。
> 评审模块不用四层记忆，不是功能缺失，而是按任务特性选对了工具 ——
> 该用检查点的地方不用向量库。

## 七、数据设计

```sql
-- 一次评审会
review_session(
  session_id, plan_title, plan_text, student_id,
  status, round, created_at
)

-- 质询记录（核心表）
review_question(
  id, session_id, round, speaker_role,       -- tech/cost/compliance/user
  question_type,                             -- main / cross / followup
  question, target_speaker,                  -- 交叉质询时指向被反驳的评审
  student_answer, verdict, verdict_comment,  -- resolved/partial/unresolved + 判定理由
  severity, followup_depth, created_at
)
```

> 只有这两张表。原计划里还有一张 `review_score`（四维能力诊断），本轮不做，已经从库里删掉了 ——
> 留着一张永远不写数据的表，只会让人以为那个功能还在。

`speaker_role` + `question_type` 两个字段就能还原出"谁问了谁、是主问题还是接话"，这是演示时间线的基础。

## 八、分阶段实施计划

| 阶段 | 内容 | 验收标准 | 工期 |
|---|---|---|---|
| **M1** | 方案提交（文本/Word/PDF）+ 方案要素抽取 | 提交一段方案，看到结构化要素表 | 1 天 |
| **M2** | 4 位评审 persona + 顺序轮询发言 | 一次跑出 4 个**明显不同视角**的问题 | 2 天 |
| **M3** | **交叉质询**（评审互相接话）+ 防跑偏上限 + SSE + 前端页面 | 能出现"成本评审接技术评审的话"，且不会无限互怼 | 2 天 |
| **M4** | **学生回答 + 追问（最多 1 层）** | 评审问完能停下来等学生答，答不好会被追问一层 | 1.5 天 |
| **M5** | **会议纪要 + 未答好的问题清单** | 开完会能看到质询记录时间线，以及按严重度排好的未答好清单，落库可回看 | 1 天 |

**本轮做 M1~M5。** 原计划 M5 里的四维雷达图与导出**不做**；M6（演示脚本固化 / 模型失败降级）**暂时移出**，后续再议。

M1~M5 合计约 7.5 天，比 A12（三个模块、知识点树/DAG/RAG/理解度/TTS）少一半以上，且**不需要 RAG、不需要知识点树、不需要向量库、不需要 TTS**。

> 追问为什么定 1 层而不是 2 层：4 位评审各追一层，学生就要多答 4 轮，答辩现场演示时长撑不住。
> 机制本身是按层数写的（`followup_depth < MAX_FOLLOWUP`），改一个常量就能变成 2 层，不是砍功能。

## 八之二、M2 实测结果（已跑通）

> 这一节是**实测数据**，不是设想。测试样本：`data/demo_plan.txt`（706 字的开题方案）。
> 用的是本地 `qwen2.5:7b`（最弱的通道，能跑通就说明商业模型只会更好）。

**四位评审各出一题：**

| 评审 | 提出的问题 |
|---|---|
| 技术评审 | 在仅有 5000 名学生的规模下，依赖大语言模型进行匹配推荐是否属于过度设计？ |
| 成本与进度评审 | 接入大语言模型帮助买家问成色等问题每个月大概要花多少钱？ |
| 合规与伦理评审 | 买家与卖家的聊天记录将如何存储和管理？ |
| 用户与价值评审 | 你们了解到了多少本校学生的真实需求？ |

**客观指标：**

| 指标 | 结果 |
|---|---|
| 出题数量 | 4/4 |
| 两两视角相似度 | 最高 0.07，平均 0.03（越低越说明视角不重复） |
| 人设越界（问了自己不该问的） | 0/4 |
| 一问多问 | 0/4 |

**结论：四个人设确实是四个视角，不是四个 AI 说一样的话。命题成立。**

调试中暴露并修掉的三个真问题（都固化进了实现，答辩时是可讲的工程细节）：

1. **模型会脑补方案里没有的信息** —— 7B 模型把"5000 名学生"说成"这么大规模"，然后追问 TPS。已在评审提示词中加硬约束：**提问只能使用要素表里已有的信息**。
2. **"只问一件事"靠提示词约束不住** —— 改成代码兜底 `first_question()`，只保留第一个问句。理由不是美观，而是**判定是一问一判**：一句话塞三个问题，根本判不出 resolved / partial / unresolved。
3. **缺失项不能交给模型决定** —— 某一项到底缺不缺，从字段本身就能直接判断，模型漏了就得补。已改为代码兜底 `_normalize_missing()`，模型只负责自由发挥的部分（量化指标、竞品对比、用户验证）。

这一节的三个问题，正好也回答了一个可能的质疑："四个 AI 会不会最后说一样的话" —— 有数据，不是拍脑袋。

## 八之三、M3 实测结果（已跑通）

> 分三个场景跑，跑的是**真实接口**（含 `main.py` 的路由接线）。

**场景 A：关掉接话，单独验证调度**（`max_cross_total=0`）
四位评审按 tech → cost → compliance → user 顺序各发言一次，0 次接话，会议正常结束。全通过。

**场景 B：打开接话，验证交叉质询**
一次会议产出 4 个主问题 + 最多 4 次接话，箭头方向全部正确。最好的一轮：

| 顺序 | 发言 |
|---|---|
| 1 | **技术评审**：已知你们项目目标是服务 5000 名用户，相比 MySQL 全文检索，用大语言模型进行语义匹配这一方案的准确率提升预期是多少？ |
| 2 | **成本与进度评审**：接入大语言模型作为交易助手每个月预计要花多少钱？ |
| 3 | **技术评审** ⟶ 接话 → 成本与进度评审：相比 MySQL 全文检索是否能显著提升匹配准确率，预期提升多少？ |
| 4 | **合规与伦理评审**：卖家上传的教材封面照片会存储多久？ |
| 5 | **技术评审** ⟶ 接话 → 合规与伦理评审：如果使用多模态大模型识别教材信息，这个过程是否会频繁调用模型接口，对性能和成本有何影响？ |

**第 3 条和第 5 条就是本选题的立命之本** —— 评审接住了另一个评审的话，并且从自己的关注点往下追。

**场景 C：SSE 接口**（`POST /review/meeting/start` + `POST /review/meeting/answer`，M4 起拆成两个）

| 指标 | 结果 |
|---|---|
| 请求次数 | 5（1 次开场 + 4 次交回答） |
| 事件总数 | 116 |
| 类型分布 | meeting_start 1 / elements 1 / speaker_start 8 / token 84 / speaker_end 8 / verdict 4 / await_answer 4 / meeting_end 1 / done 5 |
| speaker_start 与 speaker_end 配对 | 8 / 8 |
| 接话事件带箭头信息 | 4 / 4 |
| 收尾 | meeting_end 后接 done |

### 防跑偏三层锁

| 锁 | 上限 | 作用 |
|---|---|---|
| 每议题接话次数 | 1 | 防止一个问题被四个人轮着怼 |
| 全场接话次数 | 6 | 防止整场会议变成互相插话 |
| 同一议题已发言者不再接话 | — | 防止同一个人连说 |

外加一道**质量防线**：接话如果和对方原话、或与自己之前问过的话相似度 ≥ 0.7，自动重试一次；仍不合格就放弃这次接话，**宁可少一次接话，也不要出现"把对方的话复述一遍"**。

### 开发中挖出的四个坑（都已固化进代码注释）

| 坑 | 现象 | 原因 |
|---|---|---|
| LangGraph 静默丢字段 | 传 `max_cross_total=0` 想关掉接话，却出现了 7 次 | `ReviewState` 没声明的字段会被直接丢掉，不报错 |
| 换议题没清 `pending_type` | 新主问题被标成"接话"，验收统计全错 | 调度器只清了部分状态字段 |
| 图内连续两次模型调用 | 接话**四条全是空白**，静默走了兜底，看起来还有内容 | 内层 `astream(stream_mode="messages")` 收不到任何 chunk（实测 iter=0），改用 `ainvoke` |
| 接话炒冷饭 | 重复对方原话、或重复自己之前问过的问题 | 弱模型固有问题，加了相似度防线兜底 |

### 诚实的质量说明

机制、调度、额度、箭头**全部可复现**，但**接话内容质量在 run 之间波动明显**：有时完全不理对方，偶尔还会角色串味（技术评审去问成本问题）。

根因是本地 `qwen2.5:7b` 的能力上限，不是结构问题。**正式演示走商业模型 `qwen3.7-flash`**（代码里降级链路已就绪）。

## 八之四、M4 实测结果（已跑通）

> 同样三个场景。跑的是本地 `qwen2.5:7b`。

**场景 A：一路「跳过」—— 跨请求续接 + 跳过不追问**

一场会议拆成 **5 次请求**（1 次开场 + 4 次交回答），108 个事件。四次 `await_answer` 都带齐了"谁在问、问的什么"，学生的跳过被逐条记进 `question_log`，判定全部为 `unresolved`，**没有产生任何追问**（跳过还追问没有意义），未答好清单 4/4。

**场景 B：故意答一句空话 —— 追问机制真的会开火**

学生四次都回答同一句「这个我们后面会完善的，团队经验也比较足，您放心。」，结果 **4 个议题全部被执行了追问**，而且追问是**接着这句话往下扎**的：

| | 主问题 | 追问 |
|---|---|---|
| 技术评审 | 卖家上传教材封面照片后，系统如何处理识别失败的情况？ | 如果识别错误，系统是否有备份方案来确保用户能正确发布教材信息？ |
| 成本与进度评审 | 后端接口开发预计需要多少人月，接入大语言模型每月的调用量和费用是多少？ | 接入大语言模型功能的每月调用量预计是多少，每个月的费用预计多少？ |
| 合规与伦理评审 | 卖家上传的教材封面照片会被多模态大模型识别后存储在哪里？ | 卖家上传的教材封面照片会存储多长时间？ |
| 用户与价值评审 | 一学期只有两周有明显的需求，平台如何在其他时间留住用户？ | 一学期只有两周有明显交易需求，你们的平台在其他时间段如何获取用户数据验证这个需求的真实性？ |

**层数封顶 1 层，实测每个议题最多追 1 次，没有出现套娃。** 未答好清单 4/4。

**场景 C：不调模型的硬规则检查（这一节是防回归的）**

A/B 依赖模型输出，会随模型心情波动，但下面这几条是硬规则，必须**每次都确定地验出来**，所以单独写了一组不调模型的用例：

| 检查 | 用例 |
|---|---|
| 调度决策表 | 8 个阶段分支各走一次，确认 manager 的去向（extract / speaker / judge / 停住 / 散会） |
| 换议题清场 | 换人时 `pending_question`/`pending_from`/`student_answer`/`followup_depth`/`cross_checked` 等 8 个字段必须一起清 |
| 未答好清单归拢 | 答不上来→进清单；追问答好了→不进；追问仍没答好→进且取最严重度；没判过→不进；中间夹着接话→不影响 |

**这一节的 8 个调度分支 + 5 条归拢规则全部通过。**

### M4 定下的三条规则

| 规则 | 为什么 |
|---|---|
| **本议题的问题按提问顺序依次答**，每条由那条问题的提问者判定 | 屏幕上永远只有一条"待你回答"，不会出现"三个人一起问、我该答谁"。而且每条问题都有问有答有判定，接话不会白问 |
| **追问放在整个议题答完之后**，由"没被说服"的那位追一层 | 追问能看到本议题完整的问答，比只看到主问题答得更准；每个议题封顶 1 层，议题不会无限拉长 |
| **学生明确跳过时，不再追问** | 追问一个已经承认不会的问题没有信息量。这条还有个副作用：判定走短路不调模型，结果完全确定，验收能稳定复现 |

### 开发中挖出的三个坑

| 坑 | 现象 | 原因 |
|---|---|---|
| `await_answer` 不是"暂停"，是 `goto=END` | 第一版以为图会挂起，结果会议直接在第一次提问后结束 | LangGraph 没有"挂起"语义，续接靠的是**检查点 + 带同一个 thread_id 重新 astream**，和模拟面试续多轮是同一套路 |
| 接话改写了 `pending_question` | 学生去答接话，主问题反而没人判、进不了未答好清单 | 接话节点不该动"学生接下来回答哪个问题"这三个字段，只在 `question_log` 里留痕 |
| 三个评审一起问，只让答一个 | 界面上三条问题都像在问学生，只有一条能答；接话那条**问了没人答也不判定** | 一个议题允许多条问题、却只把主问题排进待答。已改成按提问顺序依次答（见上） |

所以这一组用合成的记录直接写库再读回，逐字段比对：

| 检查项 | 结果 |
|---|---|
| 4 条记录全部字段一致 | 通过 |
| 交叉质询的 `target_speaker` | 通过（`'cost'`） |
| 追问的 `followup_depth` | 通过（`1`） |
| 清单归拢（2 个议题都没解决） | 通过，2 条，严重度 `[4, 4]` |
| 清单带上判定理由 | 通过 |
| **重开一场是替换不是叠加**（同一 `session_id` 再开一次） | 通过 |
| 写空日志能清掉旧记录 | 通过 |

### 两个设计决定

| 决定 | 理由 |
|---|---|
| **未答好清单不单独存一张表，从质询记录推出来** | 存两份迟早会不一致。推出来的永远和判定结果对得上，连"追问答好了就不算未答好"这条规则都自动生效 |
| **清单按提问者一条，显示他最初问的那个问题，追问附在后面** | 一个议题里可能好几位评审问了话，每人一条才完整（接话那条也算）。显示最初那条问题，学生看到的是"我当时被问的是什么"，而不是被追问绕晕；追问单独挂在下面，能看出是追到第几层还没答清楚 |

### 开发中挖出的坑

| 坑 | 现象 | 原因 |
|---|---|---|
| 老库加不了新列 | `CREATE TABLE IF NOT EXISTS` 对已存在的表什么都不做，新加的 `verdict_comment` 在老库上会报 Unknown column | MySQL 没有 `ADD COLUMN IF NOT EXISTS`（那是 MariaDB 的），改成先查 `information_schema` 再 ALTER |
| 验收脚本永远返回 0 | 页面检查明明报了"未定义 `typoVar`"，退出码还是 0 | `main()` 只写报告不返回结论。已改成 `sys.exit(0 if ok else 1)`，并**故意塞了个错变量验证它真的会红** |

## 十、风险与降级

| 风险 | 应对 |
|---|---|
| 大模型不可用 | 在线失败自动切本地 Ollama（已验证 11434 在监听）；再失败降级为"预设质询模板"，会议照开 |
| 交叉质询跑偏 / 无限互怼 | 每议题接话上限 1 次 + 全会话总上限 + "必须与自身关注点相关"的 prompt 强约束 |
| 追问变成无限套娃 | 追问层数封顶（`MAX_FOLLOWUP`，当前 1 层）+ 学生明确跳过时不再追问 |
| 学生答完会议续不上（状态丢了） | 评审会状态存 PostgreSQL 检查点，学生回答带同一个 `session_id` 就能接上；进程重启也不丢 |
| 方案太长超上下文 | 先抽取「方案要素表」，评审只基于要素表提问，控制 token |
| 评审人设趋同（4 个 AI 说一样的话） | 每位评审的关注点清单写死、互相排他；生成后做一次"去同质化"检查 |
| 评分主观、难服众 | 不输出总分，输出**逐问题的客观判定**（答了/答偏了/没答），评分只作参考维度 |
| 换本地模型后结构化输出挂掉 | 已实测：**本地模型锁定 `qwen2.5:7b`，不要换 qwen3.5:9b**（详见下方实测记录） |

### 本地模型选型实测记录（2026-09 实测，避免重复踩坑）

试过把本地模型换成 `qwen3.5:9b`，结论是**不要换**，三条硬理由：

| 现象 | 数据 | 说明 |
|---|---|---|
| 默认带思考，正文被挤空 | 抽一次要素 **313.8 秒**（7B 只要 10~12 秒） | 一句话的简单提问要 5.9 秒，全部 token 花在思考上，正文返回空字符串 |
| 关思考的开关不一样 | `enable_thinking` 无效；`reasoning_effort: "none"` 有效 | `enable_thinking` 是 DashScope 的参数，Ollama 直接忽略 |
| 不支持原生结构化输出 | 走 `response_format` 会返回带 ```` ```json ```` 围栏的文本，解析必然失败 | 改成 `ToolStrategy` 可以跑通，但**是否调用工具全凭模型自己决定，时好时坏**，间歇性失败在答辩现场是致命的 |

而且换模型会连带影响原有模块：`intent_node`、`router_agent` 也走 `ProviderStrategy`，一并要改。

**决定：本地模型固定 `qwen2.5:7b`，`.env` 与 `my_model.py` 保持原样，零侵入。** 正式演示走商业模型 `qwen3.7-flash`。
